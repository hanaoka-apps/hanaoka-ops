花岡車輌 生産管理システム 概要

受注 → 計画 → 現場実行 → 進捗可視化 を一気通貫で結ぶ仕組み
作成：2026-06-02　／　対象読者：社長・営業部長・生産部長・生産管理者・班長
🎯 このシステムが目指すこと

営業の受注情報から、生産管理の日次計画、現場の実績、経営層の進捗確認までを SharePoint Lists を中心とした単一の仕組み でつなぐ。属人・紙・FAX・口頭依存を脱し、「父を見る会社」から「数字とMVVを見る会社」への移行を技術側から支援する。

データは下から積み上がる構造。日次計画が真実の源（Source of Truth）で、週次・月次は集約結果。

3. 入力フォーム（5種）

A画面営業受注入力
使用者：営業
客先選択・機種・表面処理・台数・希望納期を入力。客先3,740件・機種39件を高速検索。受注は kintone番号で一意管理。
B画面工程ルート入力
使用者：生産管理者
受注ごとに工程ルート（材料切断→サブ組→…→完組）と各工程の担当班・標準工数を設定。機種フィルタで80工程から絞り込み入力。
C画面日次計画グリッド
使用者：生産管理者・班長
Excel風2Dグリッドで日次の生産計画台数を入力。キーボード操作対応。客先納期から逆算して計画を組む基本画面。
D画面作業員アサイン
使用者：班長
ドラッグ＆ドロップで作業員を工程に当て込み。当月割当日数バッジ表示、重複アサイン警告。
E画面現場実績入力（タブレット）
使用者：現場作業員（タブレット）
1日1回、終業時に当日の生産数・工数・付随作業（段取り・修正・清掃等）・遅延理由・写真を入力。累計表示で進捗が一目で分かる。
📊 ビュー進捗ビュー（Level 1〜4）
使用者：全員
経営層・生産管理者・班長がそれぞれの粒度で進捗を確認。役割に応じてタブで切替。

5-2. CSV編集から反映までの仕組み（重要）

「自動同期」と書いていますが、CSV編集 → 即時反映ではありません。GitHub Actions が決まった時刻に動き、その時に OneDrive のCSVを読みに行ってSharePointへ書き込むため、必ず時間差があります。

反映パターン

パターン動作反映速度
① 定期実行（標準）GitHub Actions の cron 設定で毎朝6時に自動実行。前日中のCSV編集が翌朝に一括反映される。翌朝6時
② 手動トリガー情報システム担当者が GitHub Actions の「Run workflow」ボタンを押して即時実行。急ぎ反映が必要な時に使用。数十秒〜2分
③ 変更検知（オプション）Power Automate で OneDrive のCSV更新を検知 → GitHub Actions API を自動起動。要追加実装。1〜5分
📌 推奨運用：①＋②のハイブリッド
日常運用は「①毎朝6時の自動実行」で十分。急ぎ反映が必要な時のみ、情報システム部門が「②手動トリガー」で対応。マスタは毎日大量に変動しないので、これでガバナンスとスピードのバランスが取れます。

5-4. 試験運用（Step 9 Light）について

本格的な Step 9（Azure AD認証統合・堅牢化・最適化）を一気に進める前に、軽量版での試験運用を挟むことを推奨します。

現状の認識

現在お渡ししているA〜E画面・進捗ビューはすべて モックアップ（プロトタイプ）。データは JavaScript内に固定値として埋め込まれており、SharePoint と接続されていません。試験運用するには、各画面に SharePoint接続を実装する必要があります。

7. このシステムの重要な設計思想

思想内容
日次が真実の源計画立案は日次。週次・月次は集約結果（自動再計算）。現場と経営が同じ数字を見る。
月コミット数は不変客先への納期約束は営業側で管理。月途中で勝手に動かさない。変更は営業承認フロー経由。
週次リプランは可変進捗を見て毎週の作業計画を更新。ただし変更理由を PLAN_HISTORY に必ず残す。
属人脱却客先重複は社内一意化、機種マスタは全39を統一、工程は標準ルート。「あの人がいないと分からない」を構造的に解消。
MVV準拠「DANDYであれ」（誠実・反省・挑戦）を仕組みで支援。計画変更理由を残すのは紳士的姿勢の表現。
