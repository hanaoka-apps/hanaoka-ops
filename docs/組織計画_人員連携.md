# 組織計画と人員表の連携

更新日：2026-11-18。初回の実データ照合、自動追加、SharePointへの保存・再読込を確認済み。全利用者の権限と同時編集は未確認。

## 決めたこと

- 現在の人員はワークフローの人員表を読み、将来案は組織計画で編集する。
- 社員・契約・パート・特定技能・役員が対象。募集枠・派遣・シルバー・スポットは取得対象外。募集のリストを読まず、組織計画内に作った募集案は残す。
- 年齢は表示年度の開始直前の3月31日時点の満年齢。2026年度なら2026/3/31。生年だけの旧データから月日を推測しない。生年月日未取得は年齢未確認とし、平均年齢の計算から除く。
- 人員の在籍表示は年度中の現状と年単位の予定。3月31日にいた人を復元した名簿ではない。年度途中の入退社を日単位で見る機能は今回の対象外。

## 取得と保存

`org_staff.js` が共通認証の `graphGet` を使い、ワークフローと同じサイトの `STF_Person` を全ページ取得する。氏名・従業員コード・所属パス・役職表示・区分・在籍状態・入退社日だけに絞って保持する。正式部門は `STF_Unit` の有効な `Path` と在籍者の所属パスを使う。本社・工場と営業・ソリューション・業務センターなどのパスから表示グループを自動分類する。部門一覧の取得失敗時は在籍者の所属を使う。空の旧部門を組織図・年齢推移表に並べない。

給与の `history/employee_master.json` は最新月を選び、従業員コードが一件だけ一致した場合に生年月日と入社日を補完する。コードが複数に一致する場合は、同じコードの中で氏名も完全一致する一件だけを使う。それでも複数・不一致の場合やコード欠損では補完しない。人員の更新では給与金額を取得しない。「等級・年収」を開くと給与を自動取得し、基本給・役付手当を試算に使う。人事原本にある未使用項目は保存用データに写さない。

保存先は既存の限定サイトの `組織計画/org_plan.json` のみ。元の人員表・給与には書き戻さない。利用ログ・コンソール・リポジトリ・資料に実際の氏名・年齢・金額を記録しない。元の人事原本も保存しない。

追加する項目：

- `staffSync.baselineId`：現状として更新する案。誤った切替を防ぐため、設定後は画面から切り替えない。連携中の現状の案は削除できない。
- `staffSync.autoAdd`：初回の対応確認後に開始する、現状の案への新しい人の自動追加。
- 各案の人の `staffId` / `empCode`：人員表のIDと従業員コード。各案の中では同じIDを二人に割り当てない。
- `birthDate`：生年月日。`birth` は旧形式との互換のため残す。
- `sourceState`：取得した在籍状況。将来案を退職扱いに変えるためには使わない。
- `sourceDept` / `sourceYear`：将来案でも使う現在所属の基準。基準年度より後の異動予定は優先する。元の所属・予定は消さない。
- `staffSync.deptAliases`：確認済みの紐付けから得られる旧部門名と正式部門の対応。複数候補は共通する正式階層までにとどめ、拠点をまたいで確定しない。
- 現状の案の `people[].actualHistory[]`：年度・所属・役職・在籍状態・入退社日。同じ年度は最新の状態に置き換え、過去年度の記録は残す。導入前の状態は、既存の計画データのままなので実績とは断定しない。

人のIDと案ごとの予定を分けているため、今後、想定年収を従業員コードと年度・案で結び付ける余地がある。今回、未使用の金額欄は増やさない。

## 初回の操作

1. 本番の限定サイトで旧データの控え・閲覧者の権限を確認する。
2. 「人員表との連携」を開き、案・氏名・所属・従業員コードを見比べる。一件に決まる氏名・コードは候補として表示するだけで、まだ接続しない。
3. チェックした一致候補をまとめて結び付けるか、一人ずつ確認して結び付ける。名字だけ・同姓同名は手で対応を選ぶ。案が複数あれば、各案の対応を確認する。
4. 現状として更新する案を選び、設定ボタンを押す。所属・役職は人員表の内容が優先されるので、検討中の案は事前に別の案として残す。
5. 現状の案の対応を全員確認したら、自動追加を開始する。人員表にいる未登録の在籍・退職予定・入社予定の人が追加される。退職者は新規追加しない。将来案への追加は個別に選ぶ。
6. 正式部門の表示グループは自動で分類される。計画用の独自部門だけ必要に応じて指定する。

結び付けた人の氏名・生年月日・入社年は各案で更新する。所属・役職・等級・在籍状況は現状の案に年度ごとの記録として反映する。将来案も現在所属を正式な人員表から表示し、その後の異動・昇格・等級・退職想定・募集・役割・メモは保持する。現状の案をコピーすると、その時点の所属・役職を持つ将来案になる。

読み込みは起動時・「人員を読み直す」・画面表示中の5分ごと。編集中・保存中・右のパネルや連携設定を開いている間は定期更新を見送る。閉じているアプリでは処理しない。取得失敗・空の名簿・元から見つからなくなった人は、自動退職・削除にせず前回の情報を残す。給与が読めない場合は、前回の生年月日を残して警告する。

## 保存の注意

既存の4秒後の自動保存を使う。別の場所で `updated` が変わった場合、自動保存は止めて知らせる。手動保存は既存の上書き確認を残す。保存中に追加した編集を「保存済み」としない。厳密に同時の保存を防ぐサーバー側の条件付き更新は未実装のため、同時編集時は変更内容を見比べる。

## 等級・在級期間・概算年収

「等級・年収」タブで等級別の人数・個人一覧・確認できる在級期間・概算年収を表示する。詳しくは [組織計画_等級と年収](組織計画_等級と年収.md)。給与原本の形式と取得先は実データで確認。給与の自動取得と案の切替はサンプルでも検証する。役員は賞与の対象外とする。

MVVに沿っているか：日々の正しい人員情報を将来の人づくりにつなぐ。花岡車輌らしいか：二重入力を減らし、現場で維持できる構成とする。

## 定年の共通ルール（2026-11-18）

社員・特定技能は65歳定年。役員・パート・契約には自動定年を設けない。雇用区分・生年月日が確認できない人は推測しない。年度の開始直前の3/31で65歳になる年度から将来計画の不在とし、組織図・年齢推移・給与集計で共通の在籍判定を使う。現在の年度の在籍は正式人員表を優先する。

旧案の `retire` は異なる定年前提が混在しているため、保存済みの値を消さず、表示と試算で共通ルールに置き換える。人員表の実際の退職は維持し、今後画面から登録する個別の退職予定は `retireReason: personal` として定年と区別する。現状から案をコピーする際の実退職は `retireReason: actual`。自動定年なしの区分でも個別・実際の退職は有効。
