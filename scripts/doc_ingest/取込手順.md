# 書類取込エージェント 手順

福田さんのPCで定期実行される Claude が、この手順に従って
スキャンされた書類を読み、書類管理システムの台帳に流し込む。

対応する画面は `doc_management.html`（書類管理システム）。

---

## 全体の流れ

```
  複合機でスキャン
        ↓
  <スキャンフォルダ>\*.pdf   ← 場所は scan_dir.local に書く（.gitignore済み）
        ↓  ← ここから下がこの手順
  ⓪ 台帳の写しを読む    書類管理/_台帳の写し.json
  ① 新着を検出          new_scans.sh
  ② PDFを読む           1本ずつ中身を読み取る
  ③ 原本をコピー        書類管理/原本/YYYY/
  ④ 取込票を書く        書類管理/_取込待ち/YYYYMMDD_HHMM.json
        ↓  ← OneDriveの同期がSharePointへ運ぶ
  ⑤ 福田さんが画面を開く → 台帳に登録される（アプリが自動でやる）
  ⑥ 福田さんが内容を確認・修正
```

### この作りにした理由

**エージェントに書き込み権限を持たせない。**
台帳に行を作るのは、常にサインインした福田さんの権限。
エージェントは同期フォルダにファイルを置くだけなので、
このPCに認証情報を一切置かずに済む。

**原本は消さない。読み終わったら `_取込済` へ移すだけ。**
スキャンフォルダのファイルは削除もリネームもしない。
原本フォルダへのコピーが**中身まで一致する**ことを確かめてから、
スキャンフォルダ直下の `_取込済/` へ移す（2026年11月から。福田さんの依頼）。
これでスキャンフォルダ直下には未読の書類だけが残り、間違って消しても戻せる。
アプリ上の「対象外」も台帳の行を隠すだけで、書類そのものは消えない。

---

## ⓪ 台帳の写しを読む（毎回いちばん最初に）

`書類管理/_台帳の写し.json` は、アプリが読み込み・保存のたびに書き出す台帳の中身。
**エージェントは台帳を直接見られないので、これが「いまの台帳」になる。**
自分が前に書いた取込票（`_取込済`）ではなく、こちらを正とする。人が画面で直した結果が入っているため。

先頭の `writtenAt` が書き出した日時。何日も前なら、福田さんにアプリを一度開いてもらうよう
報告に書く（そのまま進めてよいが、最近の修正が入っていないことを前提にする）。

読んだら、新しい書類を読むときに次のように使う。

| 見るところ | 使い方 |
|---|---|
| `fileName` | 同じ書類がもう台帳にあるか（重複スキャンの見つけ方は、件名・差出元・日付・金額も見る） |
| `data.keys`・`sender`・`title` | 新しい書類の続き・元になった書類を探す。見つけたら `checkPoints` に「台帳の○○（ファイル名）の続き」と書き、`threadId` が付いていればそれを入れる |
| `taskStatus`・`data.task` | 新しい書類で済んだと分かるタスク（入金の通知・受付の控え・領収書など）があれば、修正票で `完了` にする（下の⑤-2） |
| `status` が `対象外` の行 | 人が要らないとした種類。同じ種類の新しい書類は、その旨を `checkPoints` に書き、信頼度を下げる |
| 人が直した項目 | 自分が前に書いた取込票と比べて、件名・区分・差出元・タグの直され方を真似る（福田さんの好みが出ている） |
| `data.notes` | 人のメモ。判断の手がかりになる。**取込票で上書きしない** |
| `data.deadlines` | 期限台帳。新しい書類で日付が変わったら（更新・延長・解約）修正票で直す |
| `data.links` | 人が確定したつながり。同じ案件の新しい書類が来たら同じ `threadId` を使う |

本文（`fullText`）は写しに入れていない。要るときは `_取込済` の取込票か、`原本/` のPDFを見る。
**写しを直しても台帳には戻らない。** 直すときは修正票を書く。

---

## ① 新着を検出

```bash
bash scripts/doc_ingest/new_scans.sh
```

スキャンフォルダにあって `書類管理/原本/` に無いPDFを出す。
状態ファイルは持たない（ズレる・壊れる・消えるため）。
「原本フォルダに置いてあるか」だけで判定している。

初回は過去分も全部出る。1回で全部やらず、**1回あたり10〜20件まで**にして
何回かに分ける。古いものから順に処理する。

## ② PDFを読む

スキャン画像なのでテキスト層は無い。**Readツールで直接PDFを開いて目で読む。**
`pdftotext` は空を返すので使わない。

読みながら、次を拾う。

### 必ず拾うもの

| 項目 | 補足 |
|---|---|
| タイトル | 「誰から・何の書類か」が一目で分かる日本語。ファイル名は使わない |
| 会社 | `花岡車輌` か `ハナオカ`（株式会社ハナオカ宛・ハナオカ名義のもの）。経理上は別会社なので必ず分ける |
| 差出元 | **会社名だけ**（「株式会社」は付けない）。支店・部署・担当者は入れない（→担当・連絡先へ）。自社が出したものは `花岡車輌（自社）`。下の「差出元の書き方」を見る |
| 担当・連絡先 | 支店・部署・担当者名・TEL・FAX |
| 書類種別 | **下の10種から1つ**。「案内＋契約書」のような細かい言い方は `docTypeDetail` に |
| カテゴリ | 下の一覧から選ぶ |
| タグ | 下の一覧から当てはまるものを**いくつでも** |
| 文書日付 | 書類に書かれた日付。和暦は西暦に直す（令和8年＝2026年） |
| 受領日 | スキャン日（ファイルの更新日時） |
| 金額 | 税込の総額。**「その書類の主たる金額」が1つに定まらないなら空にする** |
| 識別番号 | 契約No・証券番号・取引番号・登録番号・車台番号など。**つながりの手がかりになるので漏らさない** |
| 要約 | 3〜6文。何の書類で、何が書いてあり、何が起きるか |
| 要確認ポイント | 期限・読み取れなかった箇所・違和感 |
| 全文テキスト | 読み取れた文字を可能な限り。**検索はここに当たる** |

### カテゴリ

`金融・銀行` / `リース・車両` / `購買・契約` / `保険` / `税務` /
`人事・労務` / `社内稟議` / `その他`

`売上・請求` / `支払・経理` / `リース・設備` / `法務・登記` / `通信・IT` も使っている。
カテゴリは増やしすぎない。細かく分けたいときはタグを使う。

### 書類種別（この10種から1つ。自由に書かない）

`請求書` / `明細・計算書` / `契約書` / `案内・通知` / `証明書` / `申請・届出` /
`納付・税` / `社内資料` / `行政の指導・報告` / `その他`

★最初は書類ごとに自由に書いていたら種類が増えすぎて、絞り込みに使えなくなった。
「購買申請（承認）書＋関税額確認表」のような細かい言い方は `data.docTypeDetail` に残す。

### 差出元の書き方

- 会社名だけ。`株式会社` は付けない（`○○リース`、`○○商会`）
- 銀行は支店を付けない（`○○銀行`。支店名などは担当・連絡先へ）
- 自社が出した・書いたもの：`花岡車輌（自社）`／`ハナオカ（自社）`
- 役所は担当の部署名（`○○都税事務所`、`○○労働基準監督署`、`○○市`）
- 協会けんぽは `協会けんぽ`
- 従業員が出したもの（退職届・就労証明の依頼・在留カードの写し）：`従業員（本人）`
- すでに台帳にある書き方に合わせる（アプリの「差出元」の絞り込みに出ている名前）

### タグ（いくつでも）

`借入` `預金` `カード` `配当・株式` `労基対応` `社保・給付` `労働保険` `入退社` `外国人雇用`
`派遣` `リース` `車両` `保険` `海外送金` `輸入` `売掛・入金` `税` `登記・担保` `通信・IT`
`展示会` と、案件の名前。ほかに次の2つは意味が決まっている。

- `取扱注意`：個人名と金額・健康情報・在留資格など、見せる相手に気をつける書類
- `定期`：毎月・毎期に届く書類（下の「定期の書類」も見る）

### 定期の書類

カード明細・配当金計算書・当座勘定や預金利息のお知らせ・財形明細・月次の支払明細表・
電気料金・社労士の報酬など、**毎月・毎期に届いて、見なくても困らないもの**は
`data.periodic: true` とタグ `定期` を付ける。アプリが取り込んだ時点で確認済みにするので、
未確認の一覧に本当に見るべきものだけが残る。**タスクがある書類には付けない。**

### そのほか拾った項目

`extra` に好きなキーで入れる。**台帳の列は増やさなくてよい。**
書類は種類が読めないので、固定の枠に押し込めない。
契約なら契約条件、車なら車台番号と走行距離、保険なら補償内容、
その書類で意味のある項目をそのまま入れる。

## ③ タスクにするかどうか

**「読んだ人が何かしないと不利益が出るか」** で決める。
出るならタスク、出ないなら保管のみ。

タスクにする例:

- 返送・回答が要る（承諾書、アンケート、確認依頼）
- 期日までに判断が要る（満期、契約更新、リース満了）
- 支払予定に載せる必要がある（契約書・請求書）
- 手続きしないと権利が消える（**証書の返却請求など、本文の末尾に紛れていることが多い**）

タスクにしない例:

- 定期的に届く残高・実績の明細（保管のみ）
- 既に引落・振替が済んでいるもの
- 過去分の控え

期限は**書類に書かれた日付をそのまま使う**。
「本状受取後1ヶ月以内」のような相対期限は、受領日から計算したうえで
**要確認ポイントに「実際の到着日が不明」と必ず書く**。
勝手に確定した日付だけ置いていくと、後で誰も疑わなくなる。

`task.why`（なぜタスクにしたか）を必ず書く。
福田さんが「これは要らない」と判断するための材料になる。

### やること／確認（`taskKind`）

- `やること`：自分たちで手を動かすもの（返送・記入して提出・振込・申告・判断・契約を交わす）
- `確認`：確かめて済んでいれば完了にするだけのもの（入金されたか・提出済みか・点検を受けたか）

確認は画面でまとめて完了にできる。迷ったら `やること`。

### 何か月も先の期限は「期限台帳」へ（タスクにしない）

**期限が4か月より先**のもの（リース満了・在留期限・役員改選・融資の金利見直し・
定期預金の満期・保険の満期・契約の縛りの満了など）は、タスクではなく
`data.deadlines` に入れる。日が近づくと（60日前から）アプリがタスクの一覧に出す。

```json
"deadlines": [
  { "date": "2027-06-29", "label": "○○ 再リース満了" },
  { "date": "2027-04-29", "label": "○○ 再リースの回答期限", "note": "何もしなければ自動で1年更新" }
]
```

タスクにしなくても、**満了日・更新日・見直し日は台帳に載せておく**（保険の満期・ドメインの
有効期限・契約期間の満了など）。忘れると困る日付を、書類を開かなくても一覧で見られるようにするため。

## ④ 信頼度

| 値 | どういうとき |
|---|---|
| `高` | 主要項目が全部くっきり読めた |
| `中` | 読めたが、解釈に迷う箇所がある（金額がどれを指すか等） |
| `低` | **読み取れなかった項目がある／差出元が特定できない／期限が推定** |

**迷ったら低に倒す。** 高くしておくと誰も見直さない。
低いものは画面上で赤く出て、福田さんの確認が入る。

## ⑤ 原本をコピーして取込票を書く

原本:

```
書類管理/原本/<文書日付の年>/<元のファイル名のまま>.pdf
```

ファイル名は変えない。スキャンフォルダの原本と突き合わせられなくなる。

取込票:

```
書類管理/_取込待ち/<YYYYMMDD_HHMM>.json
```

複数件を1つの取込票にまとめてよい。形式:

> このリポジトリは**公開**されている（GitHub Pagesで配信）。
> ここに書く例は**必ず架空の値**にすること。実物の契約番号・車両番号・
> 取引先の担当者名や電話番号を書かない。

```json
{
  "generatedAt": "2026-09-16T18:45:00+09:00",
  "agent": "claude-doc-ingest",
  "items": [
    {
      "sourcePath": "<スキャンフォルダのフルパス>\\20260916165758400.pdf",
      "filePath": "書類管理/原本/2026/20260916165758400.pdf",
      "fileName": "20260916165758400.pdf",
      "title":    "リース契約満了のご案内（○○工場 △△車）",
      "category": "リース・車両",
      "company":  "花岡車輌",
      "docType":  "案内・通知",
      "sender":   "○○リース",
      "docDate":  "2026-07-31",
      "received": "2026-09-16",
      "due":      "2026-10-09",
      "amount":   270600,
      "taskStatus": "未着手",
      "taskKind": "やること",
      "data": {
        "docTypeDetail": "案内＋契約書",
        "senderContact": "○○リース株式会社 ○○支店 営業一課 担当者名 TEL 000-000-0000",
        "tags":          ["リース", "車両"],
        "confidence":    "高",
        "summary":       "…3〜6文…",
        "checkPoints":   "★満了日 2026年10月9日まで。…",
        "keys":          ["<契約番号>", "<登録番号>", "<車台番号>"],
        "extra":         { "契約番号": "…", "走行距離": "…" },
        "task": {
          "title": "再リース契約承諾書を返送",
          "owner": "総務部",
          "why":   "満了日が2026年10月9日。終了なら当日返車が必要なため。"
        },
        "deadlines": [ { "date": "2027-10-09", "label": "△△車 再リース満了" } ],
        "fullText": "…読み取れた文字を可能な限り…"
      }
    }
  ]
}
```

- 日付は全て `YYYY-MM-DD`。和暦は西暦に直す
- `amount` は数値（カンマ・円マーク無し）。定まらないなら `null`
- タスクが無い書類は `data.task` と `taskKind` ごと省く
- 定期の書類は `data.periodic: true`（タスクは付けない）
- `filePath` は `ドキュメント` ライブラリから見た相対パス

書いたらそこで終わり。**台帳への登録はアプリがやる。**

## ⑤-2 登録済みの行を直す（修正票）

あとから分かったこと（タスクが済んだ・会社が違った・重複だった など）は、
同じ取込票の形で `"op": "update"` の行を書けば、アプリが登録済みの行を直す。
原本のファイル名で行を探し、書いた項目だけを変える。人が画面で書いたメモ・つながりは触らない。

```json
{ "op": "update", "fileName": "20260101090000000.pdf",
  "set":  { "company": "ハナオカ", "docType": "案内・通知", "sender": "○○銀行", "taskKind": "確認" },
  "data": { "tags": ["預金", "定期"], "periodic": true, "docType": null },
  "unset": ["task"],
  "statusIfUnconfirmed": "確認済",
  "status": "対象外" }
```

- `set`：列の値（title / category / sender / company / docType / taskKind / due / taskStatus / threadId）
- `data`：Data に足す・上書きする項目。`null` を入れると消す
- `unset`：Data から消す項目。`task` を消すとタスクも「なし」になる
- `statusIfUnconfirmed`：まだ未確認のときだけこの状態にする（人が確認済みにしたものは戻さない）
- `status`：状態を必ずこれにする（重複を対象外にするときなど）

ファイル名が台帳に無い行は失敗し、その取込票は `_取込待ち` に残る（直して更新を押せば残りだけ入る）。
**修正票は、その書類を登録する取込票より後の名前にする**（名前の順に処理するため）。

## ⑥ つながりについて

取込時に無理に繋げようとしなくてよい。
`keys` をきちんと拾っておけば、**アプリ側が「これ、つながっていませんか？」と
候補を出す**。確定するのは福田さん。

ただし、台帳の写し（⓪）で前の書類が見つかったら、
`checkPoints` に「○月○日の△△（ファイル名）と同一案件の可能性が高い」と書いておく。
番号が違っても人は気づける。前の書類に `threadId` があれば、同じものを入れる。

## やってはいけないこと

- 台帳の写しを読まずに取込票を書く
- 台帳の写しを直接書き換える（台帳には戻らない。直すときは修正票）
- スキャンフォルダの原本を削除・リネームする
- コピーの照合（中身の一致）を確かめる前に `_取込済` へ移す
- 在留カード番号・マイナンバー・病名・生年月日・口座のパスワードなどを台帳に転記する
  （原本は限定サイトにあるので、台帳には「何の書類か」と期限だけ書けばよい）
- 認証情報をこのPCに保存する
- 読み取れなかった項目を、それらしい値で埋める
  （空にして信頼度を `低` にする。埋めると誰も気づけない）
- 1回の実行で大量に処理して、確認しきれない量を福田さんに渡す
