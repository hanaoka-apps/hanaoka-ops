# EC売上：SMILE取込のPADフロー作成手順（RPA専用機で人が作る）

「SMILEに取り込む」ボタンから始まる取込のうち、**専用機の人が作るPADフロー3つ**の手順書です。
全体の約束事（置くファイル・manifest・result.json・管理者確認・二重取込防止・30日で削除）は
`EC売上_RPA専用機への依頼内容.md`、キューの仕組みは `新PC引き継ぎ.md` を先に読んでください。
常駐スクリプト（`scripts/rpa_queue_worker.ps1`）は、ファイルの確認・配置・フローの起動・`result.json` の作成までを自動でやります。
**PADフローが担当するのは「SMILEの画面操作」と「結果ファイルを書くこと」だけ**です。

## 全体の流れ（常駐スクリプトとPADの分担）

```
常駐スクリプト                              PADフロー
────────────────────────────────────────────────────────────────
管理者確認・二重取込確認・ファイル照合
固定フォルダ C:\RPA\ec_import\current\ に
  納品先.txt・受注.txt を置く
  ① Smile_EC納品先取込 を起動  ───────▶   SMILE に 納品先.txt を取り込む
                                           result_nouhin.json を書く
  result_nouhin.json の出現を待つ ◀──────
  （エラーがあれば ② は実行しない）
  ② Smile_EC受注取込 を起動    ───────▶   SMILE に 受注.txt を取り込む
                                           result_juchu.json を書く
  result_juchu.json の出現を待つ ◀──────
_rpa_import\<バッチ番号>\result.json を書く
done / failed へ移す
ec_smile_verify_export を依頼に追加 ───▶   ③ Smile_EC確認用出力（全件出力）
                                           受注明細出力.csv・納品先マスタ.csv を
                                           SharedMasters 直下に上書き（夜間と同じ名前・全件）
フロー完了後、build_ec_index.py を実行
  → SharedMasters\ec_smile_index.json（アプリが突き合わせに使う軽量ファイル）
```

- PADフローは URI（`ms-powerautomate:/console/flow/run?workflowName=…`）で起動され、**完了を待たずに戻る**。常駐スクリプトは「結果ファイルが起動後に現れたら終わり」と判断する。
  だから結果ファイルは**フローの最後に**書くこと（途中で書くと、SMILEの操作が終わる前に次へ進んでしまう）。
- 固定フォルダ `C:\RPA\ec_import\current\` は先に作り、PADを動かすユーザーに書き込み権限を付けておく。置き場所を変えるときは `rpa_queue_worker.ps1` の `$EcImportCurrentDir` を直す。
- 固定フォルダのファイルは、常駐スクリプトが取込のあとに**必ず消す**（お客様の名前・住所・電話が入っているため）。PADフローの中では消さなくてよい。

## フロー① `Smile_EC納品先取込`

入力：`C:\RPA\ec_import\current\納品先.txt`（UTF-16・タブ区切り・見出し付き・42列）

1. SMILE にログインしている画面を確認する（ログイン切れ・想定外のダイアログなら、手順5の「止め方」へ）。
2. 「汎用データ受入」（マスタ取込）を開き、**納品先マスタ**の取込設定を選ぶ。
3. 取込ファイルに `納品先.txt` を指定して実行する（同名の既存コードは**上書きしない**設定にする。新規コードだけが入る想定）。
4. 取込結果の画面から **取込件数** と **エラー件数**、エラーがあれば **行番号とメッセージ**を読み取る。
5. `result_nouhin.json` を書く（下の「結果ファイルの書き方」）。**SMILEの「実行」を押す直前までは `executed: false`、押したあとは `executed: true`**。
6. 画面が想定外で止まるとき（下の「失敗したとき」）：
   - 「実行」を押す**前**なら、`executed: false` で結果ファイルを書いて終わる。常駐スクリプトが `failed`（再実行OK）にする。
   - 「実行」を押した**後**、または押したか分からないときは、`executed: true`（分かる範囲の件数）で書くか、**結果ファイルを書かずに終了**する。どちらも常駐スクリプトが `partial`（要確認・再実行不可）にして止める。SMILE の状態は人が見て判断する。

## フロー② `Smile_EC受注取込`

入力：`C:\RPA\ec_import\current\受注.txt`（UTF-16・タブ区切り・見出し付き・121列）

1. SMILE の画面を確認する。
2. 受注の「汎用データ受入」を開き、受注明細の取込設定を選ぶ。
3. 取込ファイルに `受注.txt` を指定する。**「新規に採番する」を必ずオン**にする（受注№・処理連番はファイルの中が仮番のため。オフだと既存の伝票を壊す）。
4. 実行して（押す直前に `executed` を `true` にする）、取込件数・エラー件数・エラー内容を読み取る。
5. `result_juchu.json` を書く（「実行」を押す前に止まったなら `executed: false`。手順は①と同じ）。

## フロー③ `Smile_EC確認用出力`（全件出力）

ジョブ `ec_smile_verify_export`（`rpa_jobs.json`）で起動される。**SMILEの出力は、全データを上書き保存する限り、日中に何度出しても問題ない**（夜間の定時出力も同じ全件出力）。なので確認用も同じ全件出力にする。**一部の内容（絞り込んだ条件パターン）で上書きしてはいけない。**

1. 既存の全件出力フロー（`Smile_日報用マスタ出力`）を**複製**して `Smile_EC確認用出力` を作る。
2. 複製したフローから、**受注明細出力と納品先マスタ出力の2つだけ**を残す（他の売上明細・目標などは外す）。条件パターンは既定（SharedMasters更新）のまま。
3. 出力先は SharedMasters 直下の `受注明細出力.csv`・`納品先マスタ.csv`（夜間の出力と**同じ名前**）。約2分の見込み。
4. 2つとも書き終わったら終了。常駐スクリプトは「2つが起動後に更新され、30秒サイズが変わらず、書き込み中でない」ことで完了と判断する（上限10分）。

そのあと常駐スクリプトが後処理 `build_ec_index`（専用機のPythonで `scripts/build_ec_index.py` を毎回GitHubのmainから取得して実行）を行い、SharedMasters直下に **`ec_smile_index.json`** を作る（ECの得意先の受注・納品先、品目、入金だけ。1MB前後。失敗したら前回のファイルが残る）。アプリはこのJSONで突き合わせる。PAD側ですることは増えない。

- 夜間の `ec_index` ジョブ（01:10）は、PADなしで `build_ec_index` だけを実行する。
- JSONの `generatedAt` が取込の完了時刻より新しくなるまで、アプリは「確認待ち」のままになる。

> 常駐スクリプトの側では、SMILEの自動起動の失敗・取込の途中で常駐スクリプトが止まった・予期しない例外でも、必ず `result.json`（`message` に理由）を書いて `failed/` へ移し、固定フォルダの中身も消す（詳細は `EC売上_RPA専用機への依頼内容.md` の 3-3b）。PADフローはこれまでどおり、結果ファイルを書くだけでよい。

## 失敗したとき（SMILEの画面が想定外だったとき）

ログイン切れ・想定外のダイアログ・待っても画面が変わらない、など。**取込は自動でやり直さない**（二重に入るのを防ぐため）。

- **工程の記録**：手順ごとに「いまの工程」（例：`納品先取込:ファイル指定`）を変数に入れ、ログ（または結果ファイルの `message`）に残す。
- **待ち時間に上限**：画面の待ちはそれぞれ上限（例：60秒）を決め、超えたら失敗として扱う。
- **失敗したら止める**：止まった工程を書いて、**Teams に【失敗】通知**を送る（工程名・バッチ番号・押したあとか前か）。
- **結果ファイル**：「実行」を押す前なら `executed: false`、押した後・不明なら `executed: true`（または書かない）。常駐スクリプトがこれを `result.json` にまとめ、再実行の可否が決まる。
- どの画面から何を読むか（件数・エラー行の取り方）は、専用機で SMILE の取込画面を実際に見て決める。ここでは決めない。

## 結果ファイルの書き方（`result_nouhin.json`／`result_juchu.json`）

固定フォルダに、**BOMなしUTF-8**で書く。形は次のとおり（件数は数字）。

```json
{ "executed": true, "imported": 3, "errors": 1, "errorRows": [ { "row": 5, "message": "得意先コードが未登録です" } ] }
```

- `executed`＝SMILEの「実行」を押したか（true／false）。**項目がない（旧形式）と、押したものとして扱う**。
- `imported`＝取り込めた件数、`errors`＝エラー件数、`errorRows`＝エラーの行番号とSMILEのメッセージ（なければ `[]`）。
- 常駐スクリプトが、これを元に最終の `result.json`（約束事の形）を作る。`state` はスクリプト側で決める：
  - エラー0件 → `done`
  - 止まった（エラーあり・結果ファイルが出ない）とき、`executed` がすべて `false`（押す前に止まった）→ `failed`（アプリは再実行を許す。取込済みの印は付かない）
  - 止まったとき、1つでも `executed: true`（押した後）か不明（結果ファイルが出ない・項目なし）→ `partial`（取込件数が0でも一部が入っているかもしれない。アプリは再実行させず「要確認」で止める）
  - 同じバッチが `failed/` にあって `executed: false` なら再実行できる。`executed: true`・不明なら、常駐スクリプトが再実行を受け付けず `partial` で止める

### PADでの書き方

1. 取込結果の件数・エラー件数を変数に入れる（画面の文字を「テキストを解析」などで数字にする）。
2. エラー行は「リストを作成 → 変数の設定」で `[{"row":5,"message":"…"}]` の形の**JSONテキスト**にしておく。
3. 「ファイルへテキストを書き込む」で、`C:\RPA\ec_import\current\result_nouhin.json` に次のテキストを書く
   （エンコードは **UTF-8（BOMなし）**。PADの既定が「UTF-8」なら BOM なし）：
   `{"imported":%取込件数%,"errors":%エラー件数%,"errorRows":%エラー行のJSON%}`
4. 書き込みは**フローの最後**。書き込みモードは「既存の内容を上書き」。

## 試運転（最初は必ずテスト用の得意先・納品先で）

本番の得意先（599801・599802）で試さない。**SMILE のテスト用の得意先・納品先 `999999`** で、次の順に1件ずつ試す。

1. **フロー単体**：手でテスト用ファイルを固定フォルダに置き、PADから `Smile_EC納品先取込` だけを実行する。SMILE の画面で、納品先が `999999` 側に1件入ったことと、`result_nouhin.json` の中身を確認する。
   同じ要領で `Smile_EC受注取込`（「新規に採番する」オンを確認）、`Smile_EC確認用出力`（受注明細出力.csv・納品先マスタ.csv が全件で更新されること）。続けて手で `python scripts\build_ec_index.py --dir <SharedMastersのパス>` を実行し、`ec_smile_index.json` ができることも確認する。
2. **エラーの形**：わざと必須項目を空にしたファイルで、エラー件数・エラー行が `result_*.json` に入ることを確認する。
3. **常駐スクリプト経由（1件）**：アプリの設定を一時的にテスト用の得意先にした状態で、注文を1件だけ OK にして「SMILEに取り込む」を押す。
   専用機のログ（`%USERPROFILE%\regenerate_watcher.log`）に、管理者確認 → 配置 → フロー起動 → 完了 → 確認用出力の依頼追加が順に出ることを確認する。
4. **アプリの表示**：依頼中 → 取込中 → 確認待ち → 確認OK と進み、注文が「起票済」になって SMILE の受注№が出ることを確認する。
5. **異常系**：同じ内容でもう一度押す（二重取込として止まる）、管理者でないアカウントで依頼する（権限なしで失敗＝`executed: false` なので再実行OK）、わざと「実行」の前後で止める（前なら再実行OK、後なら要確認で再実行不可）、を確認する。
   確認用出力のあと、`受注明細出力.csv` が**全件のまま**（夜間の出力と行数が同程度）であることも確認する（絞り込んだ内容で上書きしていないこと）。
6. 上がすべて通ってから本番の得意先で1件、慣れたらまとめて。

手順3〜4は、下の「テスト送信」（アプリの管理者メニュー）で、本物の注文を使わずに通しで試せる（東京 599801 に TEST… の仮の注文が入るので、終わったら SMILE で削除する）。

### テスト送信（アプリの管理者メニューから。専用機の試運転用）

アプリから**仮データ1件**を、**EC売上の東京（得意先 599801・直販EC 東京）**に送って、取込 → 確認用出力 → 突き合わせを通しで試せる。本物の注文は使わないが、**SMILE に入っている間は、東京の売上・日報に載る**（下の「5.」で削除する）。

1. 管理者でサインインし、EC売上の画面下のバーの「⋯」を開く → 「**テスト送信（仮データ1件）**」を押す（OK済の注文が0件でもバーは出る）。
2. 確認ダイアログ（『直販EC 東京（599801）に、テスト用の注文1件と、納品先 999998 を登録します。終わったら SMILE で削除してください』と客先注番・件数・金額）で OK。
3. 画面上の「**テスト送信の結果**」の枠に、依頼中 → 取込中 → 確認待ち → 確認OK／要確認 と進む（本番の注文一覧・件数・出力バーには混ざらない）。
4. 結果の見方：**一致**＝SMILE の受注№が出る。**不一致**＝項目ごとに「アプリの期待値」と「SMILE の値」が並ぶ。**SMILEに見つかりません**＝出力・JSON作成が終わっていない、またはSMILEに入っていない（専用機の `build_ec_index` が古いと、`ec_smile_index.json` に `testOrders` の欄が無く、これになることがある）。
5. 終わったら、**SMILE で次の2つを削除する**（枠にも表示される）：
   - **受注伝票**（客先注番 `TEST` ＋ yymmddHHMM の数字、枠に出る受注№。社内メモ『花岡EC（テスト送信）』）
   - **納品先 `999998`**（名前『テスト納品先（削除予定）』。今回の送信で新規に登録した場合）
   - 削除するまで、この受注は東京（599801）の売上・日報に載りうる。得意先 599801 そのものは本番の得意先なので、**消さない**。

**仮の注文だと一目で分かる印**：客先注番が `TEST` ＋ yymmddHHMM（数字は10桁で、本番の注文番号とは衝突しない）、社内メモが『花岡EC（テスト送信）』、納品先名が『テスト納品先（削除予定）』。
**本番に混ぜない仕組み**：納品先コード `999998` は、納品先コードの連番の上限（`deliveryCodeLimit`＝`099999`）より大きいので、連番の計算に入らない（範囲内のコードを設定すると、テスト送信は拒否される）。`ec_smile_index.json` では、客先注番が `TEST` で始まる受注を `orders` に入れず `testOrders` に分け、アプリの本番の件数・二重取込の確認・入金には使わない。

送る内容は `ec_sales_config.json` の `testImport`（得意先 599801。名前・担当者 000157・部門 002220・倉庫は `config.customers`／`config.warehouse` から引く。納品先 999998 の住所・電話は架空。明細は TC×1＝税抜7,000円と送料 FR×1＝税抜1,500円で、手配区分1と2の両方を通す。納期は翌営業日）。納品先 999998 が SMILE に既にあるときは、納品先ファイルを作らず受注だけ送る。
