# EC売上アプリ：RPA専用機に頼むこと（約束事・作業手順）

RPA専用機の担当の方へ。**上から順に読んで作業すれば済む**ように並べています（1〜2が「やること」、3以降が「決まりごとの詳細」）。
キューの基本は `新PC引き継ぎ.md`、PADフローの作り方と試運転は `ec_import.md` にあります。

## 0. 何が起きるか（3行）

1. 管理者がEC売上アプリの「SMILEに取り込む」を押す → 取込ファイルが SharedMasters の `_rpa_import/<バッチ番号>/` に置かれ、`ec_smile_import` の依頼が入る。
2. 専用機の常駐スクリプトが、確認（管理者・二重取込・ファイルの中身）→ PADフロー2つでSMILEに取込 → `result.json` を書く。
3. 続けて `ec_smile_verify_export`：SMILEの**全件出力**（受注明細出力.csv・納品先マスタ.csv。夜間の定時出力と同じ名前・同じ全件）→ 軽量ファイル `ec_smile_index.json` を作る → アプリがそれと突き合わせて、一致した注文だけ「起票済み」にする。

```
Shopify ──(A) 定期取得──▶ ec_shopify_*.csv ──▶ 画面でチェック・OK ──「SMILEに取り込む」(管理者のみ)
                                                                      │
   SharedMasters/_rpa_import/<バッチ番号>/ （nouhin.txt・juchu.txt・manifest.json）＋ pending に ec_smile_import
                                                                      ▼
   専用機：管理者確認 → 二重取込確認 → 中身の確認 → PAD①納品先取込 → PAD②受注取込 → result.json
                                                                      ▼
   専用機：ec_smile_verify_export ＝ PAD③全件出力（受注明細出力.csv・納品先マスタ.csv）→ build_ec_index.py
                                                                      ▼
   SharedMasters/ec_smile_index.json ──▶ アプリが客先注番で突き合わせ → 起票済み＋SMILEの受注№ ／ 違えば要確認
```

## 2. 専用機の作業（上から順に）

### 2-1. 更新を取り込む（次のPRがmainに入ったら）

- `rpa_jobs.json` と `build_ec_index.py` は、**常駐スクリプトが毎回GitHubのmainから取得する**ので、PC側の作業は不要（マージすれば反映）。
- **常駐スクリプト本体（`scripts/rpa_queue_worker.ps1`）は専用機のリポジトリのコピーから動く**ので、差し替えが必要：
  1. 専用機のリポジトリのフォルダで最新のmainを取り込む（`git pull`。そのPCのClaude Codeに「最新のmainを取り込んで」と頼んでもよい）。`rpa_queue_worker.ps1` が新しくなったことを確認する。
  2. タスクスケジューラーの「Hanaoka 再集計リクエスト監視」を**いったん終了して開始**する（常駐スクリプトは起動時にファイルを読むので、再起動しないと古いまま動く）。
  3. ログ（`%USERPROFILE%\regenerate_watcher.log`）に「監視を開始します」が出て、エラーが出ていないこと。
- 実行中の取込があるときは、終わってから再起動する（途中で止めると、その依頼は「要確認」になる）。
- PythonでSMILE出力から JSON を作るので、**標準の Python が動くこと**（`python --version`。`build_ec_index.py` は標準ライブラリだけで動く。追加インストール不要）。

## 3. 決まりごとの詳細

### 3-1. 画面の操作（アプリ側）

画面下のバーのボタンは **「SMILEに取り込む」の1つだけ**（納品先と受注伝票をまとめて登録する）。

- 押せるのは管理者だけ（2-3の一覧）。管理者でない人には「OK済 n件（取込は管理者が行います）」と出す。
- 押すと確認ダイアログ（納品先の新規件数・受注の伝票数と行数・金額合計）→ OKで取込ファイルを置いて依頼する。
- 取込後の突き合わせで一致した注文は、SMILE が付けた受注№が注文に紐づき「**確認待ち**」になる（担当者の確認OKで起票済み）。一致しない注文は「要確認」（SMILEの値とアプリの期待値を並べて表示。再取込はさせない）。
- **注文の状態の流れ**：依頼中 → 取込中 → **突合待ち**（SMILEから全件出力し、確認用ファイルを作っている間）→ **確認待ち**（突合が一致。担当者の最終確認待ち。受注№はこの時点で表示。Teams に報告済み）→ **起票済み**（担当者が画面で「確認OK」を押して確定）。突合が一致しない・一部だけ入った（partial）・結果不明は **要確認**（再取込はさせない）。
- 突合が一致しても**自動では起票済みにしない**。「確認待ち」で止め、管理者（`ec_import_admins.json` の人）が注文ごとに「確認OK」、または「確認待ちをまとめて確認OK」を押して確定する。押した人・日時を記録する。管理者でない人は押せない。
- 再実行できるのは「`state` が `failed` かつ `executed` が `false`（SMILEの『実行』を押す前に止まった）」の取込だけ。`partial`・`executed` が `true` または不明のものは、一部が入っているかもしれないので再実行させず「要確認（SMILEを見て判断）」で止める。
- **取込の前に、SMILEの最新を取り込む**：画面上部に ec_smile_index.json の作成時刻（何時間前か）を出し、**6時間以上古い**と警告する（二重取込の確認が最新のSMILEに基づかないため）。管理者には「SMILEの最新を取り込む（約3分）」ボタンがあり、押すと `ec_smile_verify_export`（全件出力＋JSON作成）を依頼して、完了を待ってから画面を読み直す。
- 確認ダイアログには「今回の取込：n件（うち納品先の新規 m件）。SMILEに実際に登録されます（手配区分1の本体は製番が付きます）」と出す。
- 予備：管理者だけに出る小さな「⋯」メニューに、ファイルの手動保存と「手で取り込んだので起票済みにする」。

### 3-2. アプリが置くもの（`SharedMasters/_rpa_import/<バッチ番号>/`）

| ファイル | 中身 |
|---|---|
| `nouhin.txt` | 納品先マスタ取込ファイル（UTF-16 BOM・タブ区切り・CRLF・1行目見出し、42列）。新規がなければ置かない。**新規の納品先のコードは仮の番号（N00001…）**。専用機が取込の直前に本当のコードに置き換える（3-3d） |
| `juchu.txt` | 受注伝票取込ファイル（同形式、121列） |
| `manifest.json` | `{ "batchId", "requestedBy", "requestedAt", "files": [{ "name", "rows", "sha256" }, …] }`。受注（`juchu.txt`）の項目には **`slips`**（伝票の数）も付く（納品先には付けない）。`slips` はバッチ番号に含めない。仮の番号を使った新規の納品先があれば **`tempCodes`**（`[{customer, temp}]`）も付く（3-3d） |

- **バッチ番号**は `ec-` ＋ 16桁の16進（ファイルの中身のsha256から作る。同じ内容なら同じ番号）。専用機はこの形以外を受け付けない。
- 依頼ファイル（pending）：`{ "job": "ec_smile_import", "requestedBy", "batchId" }`。同じ `batchId` の依頼だけをまとめ、別の `batchId` は別の仕事として順に実行する。

### 3-3. 常駐スクリプトがやること（`ec_smile_import`）

1. **押した人の確認**：`requestedBy` が `ec_import_admins.json` にあること。なければ failed（権限なし）。
2. **二重取込の確認**：`_rpa_import/done/<バッチ番号>/` があれば failed（取込済み）。`failed/<バッチ番号>/` に同じバッチがあるときは、その `result.json` の `executed` が `false` なら再実行を許し（古い failed の記録は消す）、`true`・不明（項目なし）なら再実行せず `partial`（要確認）で止める（記録は残す）。
3. **中身の確認**：`manifest.json` と実ファイルの行数・sha256、見出しの列数（納品先42／受注121）、必須項目（得意先・品目コード・数量・納期など）が空でない。だめなら failed（`executed: false`。SMILEには触らない）。
4. **PADに渡す**：固定フォルダに `納品先.txt`・`受注.txt` をコピー。
5. **PADフローを順に実行**：①`Smile_EC納品先取込` → ②`Smile_EC受注取込`。**①にエラーがあれば②は実行しない**。SMILEが閉じていれば自動起動する（**1〜3の確認がすべて済んだあと**。権限のない依頼ではSMILEを起動しない。起動に失敗したら、SMILEには触っていないので `failed`・`executed: false` の `result.json` を書いて `failed/` へ移す）。
6. **結果を書く**：PADが固定フォルダに書く `result_nouhin.json`／`result_juchu.json`（`{ executed, imported, errors, errorRows }`）を待って、`_rpa_import/<バッチ番号>/result.json` にまとめる。完了を知らせるのは `result.json`。結果ファイルが時間内（1フロー15分）に出ないときは `partial`。
7. **移す・消す**：`_rpa_import/done/<バッチ番号>/`（`done` のとき）または `failed/`（それ以外）へ移す。依頼ファイルも done／failed に移す。**30日たったら消す**（お客様の名前・住所・電話が入っているため。アプリ側の記録も30日）。
8. **続けて確認用出力**：`done` のとき `ec_smile_verify_export` を依頼に追加する（アプリが待たなくてよいように）。アプリは取込の依頼より後のこのジョブを探して待ち、90秒たっても見つからなければ自分で依頼する。

### 3-3b. どの経路で終わっても `result.json` を書く

アプリは `result.json` で完了を判断するので、**取込フォルダがあるまま `result.json` なしで終わる経路を作らない**。常駐スクリプトは次の経路でも `result.json` を書き、`failed/` へ移し、固定フォルダ（`C:\RPA\ec_import\current\`）の中身も消す。`message` には人が読める理由を入れる。

| 経路 | `state` | `executed` |
|---|---|---|
| SMILEの自動起動に失敗（管理者・二重取込・中身の確認のあと。SMILEには触っていない） | `failed` | `false` |
| 取込の途中で常駐スクリプトが止まった（PC再起動・タスク再起動。次の起動時に処理） | `partial` | **キーを書かない**（不明） |
| 取込処理の中の予期しない例外（OneDriveのロックでコピー・移動に失敗など）：PADフローを起動する前 | `failed` | `false` |
| 同：PADフローを1つでも起動したあと | `partial` | 押したと分かっていれば `true`、不明ならキーを書かない |

アプリは `executed` が `false` 以外なら「要確認」で止めるので、キーが無い（不明）ものは再実行できない。

### 3-3d. 新しい納品先のコードを専用機で決める（仕様。アプリと専用機の約束）

SMILE の納品先マスタ取込には**自動採番がなく**、取込の条件パターンは「**新規のみ**」（同一コードが既にあるとエラーチェックで止まり、何も書かない）。そこで、**新しい納品先のコードは、アプリではなく専用機（常駐スクリプト）が、取込の直前に決める**。アプリが先に番号を決めると、その間に手で登録された番号とぶつかるため。既存のお客様（名前＋郵便番号が一致）は今までどおり**本当のコード**で、アプリが決める（「新規か既存か」の判断はアプリ＝`EC.planDeliveries`）。

**0. 専用機が対応しているときだけ仮の番号を使う（切り替え。必須）**
- アプリは、**専用機の稼働の印（`SharedMasters/_rpa_queue/heartbeat.json`）に `features: ["tempDeliveryCodes"]` があり、かつ印が新しい（20分以内に更新されている）ときだけ**、仮の番号を使う（`rpaImport.tempCodes.mode: "auto"`＝既定）。それ以外（`features` が無い・印が古い・印が無い）は、**今までどおり、アプリが本当のコードを決める**（`real`）。専用機の実装が入る前に、アプリだけ先にマージされても安全にするため。
- **専用機側の必須項目**：置き換え・検証・やり直し・`assigned` の書き込み（下の 1〜4）を**実装して動作確認してから**、`heartbeat.json` に **`"features": ["tempDeliveryCodes"]`** を書く（常駐スクリプトの稼働の印の書き込みに `features` を足す）。**動作確認の前に書かない**。書けば、アプリは自動で仮の番号に切り替わる（再起動・設定変更は不要。アプリは1分ごとに印を見直す）。
  - **専用機での有効化（実装済み）**：常駐スクリプトは、専用機の中のファイル `%LOCALAPPDATA%\hanaoka-rpa\features.json`（例 `{ "features": ["tempDeliveryCodes"] }`）があるときだけ、稼働の印に `features` を書く（常駐スクリプトが実装している名前だけ）。リポジトリには書かないので、動作確認が済んだ専用機でファイルを置いたときだけ有効になる。ファイルを消せば、次の印の書き込み（5分以内）で `features` が消え、アプリは自動で `real` に戻る。再起動は不要。
  - **動作確認（2026-10-28）**：599801 で仮の番号のバッチを2つ続けて流し、1つ目は `N00001`→000038、2つ目は古い索引で 000038 を振って「納品先が存在します」になり、000039 でやり直して取り込めた（`assigned`・`retries:1`）。試験データは削除済み。
- `mode: "temp"`（明示）にした場合も、印に feature が無ければ**送信を止めて理由を出す**（誤って仮の番号が SMILE にそのまま入らないようにする安全弁）。`mode: "real"` は常に今までどおり。
- 画面は、取込のバーに「新規の納品先：取込時に専用機が番号を決めます／アプリが番号を決めます」と小さく出し、確認ダイアログにも同じ行を出す。**モードが違えば、同じ注文でも取込ファイルの中身が違うので別のバッチ番号になる**（それでよい）。
- 専用機が `heartbeat.json` の `features` を書かなくなった（古い版に戻した）場合も、印から feature が消えるので、アプリは自動で `real` に戻る。

**1. 仮の番号（アプリが取込ファイルに入れる）**
- 新規の納品先にだけ、**仮の番号** `N00001`, `N00002`, …（`N`＋5桁。バッチの中の通し番号で、得意先をまたいでも重複しない）を使う。形は `ec_sales_config.json` の `rpaImport.tempCodes`（`prefix`、`digits`、`requiredFeature`、`mode`。**`mode` の既定は `auto`**：下の「0.」）。
- **`nouhin.txt` の「納品先コード」列と、`juchu.txt` の「納品先コード」列で、同じ仮の番号**を使う。同じお客様（同じ得意先の中で名前＋郵便番号が同じ）は同じ仮の番号。
- 列の位置（0始まり。**見出しで引くのが望ましい**）：`nouhin.txt` は **得意先コード＝0列目・納品先コード＝1列目**、`juchu.txt` は **得意先コード＝3列目・納品先コード＝6列目**。
- 仮の番号は受注日・注文番号の順に決まるので、**同じ内容なら同じ番号・同じバッチ番号**（二重取込の防止はこれまでどおり）。

**2. manifest.json に `tempCodes`**
```json
{ "batchId": "ec-…", "requestedBy": "…", "requestedAt": "…",
  "files": [ { "name": "nouhin.txt", "rows": 2, "sha256": "…" }, { "name": "juchu.txt", "rows": 4, "slips": 2, "sha256": "…" } ],
  "tempCodes": [ { "customer": "599801", "temp": "N00001" }, { "customer": "599802", "temp": "N00002" } ] }
```
`tempCodes`＝仮の番号を使った新規の納品先だけの一覧（使っていなければ項目なし）。`tempCodes` はバッチ番号には含めない。

**3. 専用機がやること（置き換え → 取込）**
1. **置き換え前のファイルで確認**：manifest の sha256・列数・`slips`、さらに **`tempCodes` の仮の番号が、`nouhin.txt` と `juchu.txt` に実際にあること**（互いに一致すること）。
2. 得意先ごとに**空きの番号**を決める：最新の `ec_smile_index.json` の納品先から、**その得意先の最大のコード＋1**。飛び番（`reservedDeliveryCodes`）は避け、`deliveryCodeLimit` より大きい値は数えない（`build_ec_index.py` の `maxCode` と同じ規則）。1バッチに同じ得意先の新規が複数あれば、順に +1。
3. **列を指定して置き換える**（`nouhin.txt` の納品先コード列と、`juchu.txt` の納品先コード列だけ。ほかの文字は触らない）。**置き換えたあと、仮の番号が1つも残っていないことを確かめてから**取り込む（残っていたら取り込まず failed・`executed: false`）。
4. 取込（納品先 → 受注）。**納品先が「納品先が存在します」でエラーチェックを通らなければ、番号を1つ進めて置き換え直し、最大10回までやり直す**（やり直しは「実行」を押す前の段階なので、`executed: false` のうちにやり直す）。10回でも通らなければ failed・`executed: false`。
5. 結果を `result.json` に書く（下）。置き換えたあとのファイルは `done/`・`failed/` にそのまま残る。

**4. result.json に `assigned` と `retries`**
```json
{ "batchId": "ec-…", "state": "done", "executed": true, "retries": 1,
  "assigned": [ { "customer": "599801", "temp": "N00001", "code": "000771" }, { "customer": "599802", "temp": "N00002", "code": "000501" } ],
  "files": [ … ], "message": "", "startedAt": "…", "finishedAt": "…" }
```
- `assigned`＝仮の番号 → 専用機が決めた最終のコード。`retries`＝やり直した回数（0以上）。
- **アプリは `assigned` を読んで**、納品先コードの期待値（新規）を最終のコードにし、ドロワーの納品先欄・一覧・Teams 報告・突き合わせ（受注の納品先コードと、納品先マスタの照合）に最終のコードを使う。**仮の番号は画面に残らない**。
- `assigned` に仮の番号が無い、または `code` が空の注文は、**「要確認（納品先コードの番号を確認できません）」**。
- 納品先が「存在しない」「エラー」で止まったときの `message`（専用機が `result.json` に書く）は、そのまま画面と Teams 報告に出る。
- **後方互換**：`assigned` の無い `result.json`（旧形式・仮の番号を使わなかったバッチ）は今までどおり扱う。

**5. PAD が読む理由**：置き換えは専用機の常駐スクリプトが行い、PAD は**置き換え済みのファイルを読んで取り込むだけ**。PAD のフローは変えなくてよい（取込ファイルの形は同じ）。専用機がコードを決めるのは、SMILE の最新の納品先（`ec_smile_index.json`）を見られるのが専用機側だから。

**6. テスト送信**：同じ判定を使う（`testImport.codeMode`: **`auto`＝既定**。専用機が対応していれば仮の番号、対応していなければ固定のコード `999998`／`temp`＝明示（対応していなければ止める）／`fixed`＝常に `999998`）。仮の番号のときは、結果の枠に `assigned` の**最終の納品先コード（SMILE で削除するもの）**が出る。同じ名前・郵便番号のテスト用の納品先がすでにマスタにあれば、それを使い、納品先ファイルは作らない（毎回増やさない）。品目の安全弁（手配区分2・在庫管理なし）は変えない。

### 3-3c. PADフローの運用の注意

- **PADフローは「保存」だけでは下書き**。常駐スクリプトと、PAD の一覧からの実行は、**「公開」した版**を動かす。**フローを直したら、必ず公開する**（保存だけで古い公開版が動き続け、止まった事例がある）。
- **止まったときは、PAD が必ず `errors` を1以上にし、`errorRows` に止まった工程と理由を書く**（例：`[{ "row": 0, "message": "画面を開く(取込画面の待ち): …" }]`。専用機側で対応済み）。「実行」を押す前に止まったなら `executed: false`。
- **運用ルール**：自動取込が失敗して Teams に【失敗】【要確認】が来たら、**手で起票する前に、専用機の担当へ連絡する**（手で起票したあとに専用機で取り込んで二重取込になった事例がある）。やむを得ず手で起票した注文は、アプリで **「SMILEを見て問題なし（起票済みにする）」を押して起票済みにしておく**（二重に取り込まないため）。

### 3-4. 2つの失敗の分かれ目と `executed`

**SMILEの「実行」ボタンを押す前に止まったか、押したあとか**で扱いが変わる。

| 止まった場所 | `executed` | `result.json` の `state` | アプリ |
|---|---|---|---|
| 押す**前**（権限なし・ファイル不整合・SMILEのログイン切れ／想定外の画面で、実行前） | `false` | `failed` | **やり直しOK**（「SMILEに取り込む」をもう一度押せる） |
| 押した**後**（取込の途中・エラーが出た・件数が取れない） | `true` | `partial` | **要確認**で止める（再実行ボタンなし。SMILEを見て人が判断） |
| 押したか分からない（結果ファイルが出ない・`executed` の項目がない旧形式） | 不明 | `partial` | **要確認** |

- 押したあとは、取込件数が0でも一部が入っているかもしれないので、再実行させない。
- **PADフローでの `executed` の書き方**：結果ファイルに `executed` を入れる。**「実行」を押す直前まで `false`、押したら `true`**（押す直前に変数を `true` にして、その値を最後に書く）。途中で想定外の画面になったときも同じ。押したか分からない状況では `true` で書くか、結果ファイルを書かずに終了する（どちらも要確認になる）。
- 常駐スクリプトはこれをまとめて `result.json` の `executed`（どれか1つでも `true` なら `true`）にする。
- **ステップが「実行」を押す前に止まったとき**（PAD の結果で `executed: false`。`errorRows` の最初に止まった工程名）：常駐スクリプトは、エラー件数が0でもそのステップを**失敗として扱い、以降のステップは実行しない**。最初のステップ（納品先）なら全体は `failed`・`executed: false`（やり直しOK）。それまでに実行済みのステップがあれば（納品先は入ったが受注は実行されていない）`partial`（要確認。再実行しない。メッセージに「納品先は取り込み済み、受注は実行されていません」）。
- **実行したのに取込件数が合わない**（0件のまま終わった、など）：`done` にせず `partial`（要確認）。**受注の `imported` は SMILE の「正常件数」＝伝票の数なので、manifest の `slips`（伝票の数。`rows` は明細の行数）と比べ、納品先は `rows`（1行＝1件）と比べる**。`slips` が無い旧形式の manifest の受注と、件数を取れない旧形式（`imported` なし）は比べない。`done` になるのは、全ステップが実行され、エラー0件で、件数が合うときだけ。詳しくは `ec_import.md` の「`executed` の意味と、常駐スクリプトの扱い」。

```json
{
  "batchId": "ec-…",
  "state": "done | failed | partial",
  "message": "失敗の理由（権限なし／取込済み／ファイル不整合／SMILEのエラー など）",
  "executed": true,
  "files": [
    { "name": "nouhin.txt", "executed": true, "imported": 3, "errors": 0, "errorRows": [] },
    { "name": "juchu.txt",  "executed": true, "imported": 20, "errors": 1, "errorRows": [{ "row": 5, "message": "…" }] }
  ],
  "startedAt": "ISO8601", "finishedAt": "ISO8601"
}
```

### 3-5. 確認用出力（ジョブ `ec_smile_verify_export`）＝全件出力＋軽量JSON

SMILEの出力は**全データを上書き保存する限り、日中に何度出しても問題ない**（夜間の定時出力も同じ全件出力）。なので、取込後の確認も同じ全件出力にして、アプリは軽量JSONで確認する。**出力を一部の内容で上書きしてはいけない**（絞り込んだ条件パターンは使わない）。

| 項目 | 内容 |
|---|---|
| PADフロー | `Smile_EC確認用出力`（既存の全件出力フローを複製して、下の2ファイルだけ出力。約2分） |
| 出力（SharedMasters直下に上書き・夜間と同じ名前） | `受注明細出力.csv`、`納品先マスタ.csv`（全件） |
| 完了の判断 | 2つの出力ファイルがどちらも起動後に更新され、サイズが30秒変わらず、書き込み中でない（上限10分） |
| 後処理（`after`） | **`build_ec_index`**：専用機のPythonで `scripts/build_ec_index.py` を実行（毎回GitHubのmainから取得。環境変数 `SHARED_MASTERS_DIR`）。成功したらジョブ完了。失敗したらジョブも failed |
| `rpa_jobs.json` | `ec_smile_verify_export`：`outputs` に上の2ファイル、`timeoutMinutes: 10`、`after: build_ec_index` |

### 3-6. `ec_smile_index.json`（軽量ファイル）と `build_ec_index.py`

- 入力：`受注明細出力.csv`（約90MB）・`納品先マスタ.csv`・`品目マスタ.csv`・`入金明細出力.csv`（任意）。タブ区切り・カンマ区切り、UTF-8／Shift-JISのどれでも読む。1行ずつ処理するのでメモリは少ない（120MBで約2秒）。
- 出力：SharedMasters直下の `ec_smile_index.json`（一時ファイル→置き換え。**失敗したら前回のファイルが残る**）。
  - `generatedAt`（UTC）、`sources`（元ファイル名・更新日時・行数）
  - `orders`＝ECの得意先（599801・599802。`EC_CUSTOMERS` 環境変数か `--customers` で変更可）の受注の行（受注№・行・受注日付・得意先・納品先コード・品目コード・数量・単価・金額・納期・出荷予定日・客先注番・社内メモ・操作日付 など）
  - `nouhin`＝ECの納品先（コード・名前・索引・荷受け人・郵便番号・住所・電話）と得意先ごとの最大コード
  - `items`＝品目（コード・名前・単位・手配区分）、`nyukin`＝ECの入金
- 個人情報（名前・住所・電話）が入るが、**ログには件数だけ**を出す。サイズは1MB前後の見込み。
- アプリは、`generatedAt` が**取込の完了時刻（`result.json` の `finishedAt`）より新しくなるまで「確認待ち」**にする（古いJSONで「見つからない」と誤判定しない）。
- アプリは、突き合わせだけでなく、品目・納品先・二重取込の確認・入金の同日確認にも、このJSONを優先して使う（無いときだけ全件CSVを読む）。

- **テスト送信の注文**（客先注番が `testImport.poPrefix`＝`TEST` で始まる受注）は、`orders` に入れず `testOrders` に分けて持つ（本番の二重取込確認・件数に混ぜない）。納品先 `999998` は連番の上限（`config.deliveryCodeLimit`＝`099999`）より大きいので、`maxCode`（得意先ごとの最大コード）の計算に入れない（マスタの一覧には出る）。得意先・印・上限は設定ファイルから読む：常駐スクリプトが `ec_sales_config.json`（SharedMasters に同名のファイルがあればそれ、無ければ main から取得）を `--config` で `build_ec_index.py` に渡す。

### 3-7. 夜間のジョブ `ec_index`

0:00台のSMILE定時出力が終わったあと、**PADなし**で `build_ec_index` だけを実行する（`rpa_jobs.json` の `schedules`：`facts_only` が 01:00、`ec_index` が 01:10）。夜間出力のあとのJSONを最新にしておくためで、`facts_only` と同じ作り。

### 3-8. 突き合わせの内容（アプリ側）

客先注番（Shopifyの注文番号）で、「取り込むはずだった内容」と `ec_smile_index.json` の受注を比べる：品目コード・数量・単価・金額（1円の端数まで）・納期・出荷予定日・納品先コード・社内メモ・行数。新規の納品先は、コードがマスタにあり、名前・住所・電話が合うか。SMILEが自動で付ける項目（製番など）は比べない。**一致しなければ「要確認」**。見つからないときは「出力・JSON作成が終わっていない可能性／SMILEに入っていない可能性」と表示する。

### 3-10. 担当者への報告（Teams のチャネル。ジョブ `ec_report`）

突合の結果が出たら、アプリが専用機に報告を依頼し、専用機が **Teams のチャネル**へ投稿する（報告先は Teams のチャネルと、アプリ画面のステータス「確認待ち」の2つ）。

- **報告の中身**：件数サマリ（取込 n件・一致 n件・要確認 n件・納品先の新規 n件）、一致した注文の「注文番号・受注№・出荷予定日」の一覧、要確認の注文とその理由（項目名。金額・数量・品目コード・納期などの値は出すが、**お客様の名前・住所・電話・社内メモの値は入れない**）、アプリのURL。長いときは3,000字ごとに分けて、続きに（1/3）のような番号を付ける。
- **依頼**：`rpa_queue.js` の `request('ec_report', { batchId, params: { batchId, parts: [本文, …] } })`。`rpa_jobs.json` の `ec_report` は `type: notify`（PAD も SMILE も使わない。依頼ごとに別の仕事として1件ずつ実行）。
- **専用機がやること**（`rpa_queue_worker.ps1` の `Invoke-Notify`）：`params.parts` を一時ファイルに書き、`scripts/post_teams.py`（毎回 main から取得。`requests` が必要）を実行する。投稿先 URL は**専用機の環境変数 `EC_TEAMS_WEBHOOK_URL` だけ**に置く（リポジトリ・アプリ・ログ・エラー文に出さない。常駐スクリプトの起動後に設定した場合も、ユーザー環境変数から読む）。**未設定なら投稿せず、「Teams への投稿先が未設定です（… EC_TEAMS_WEBHOOK_URL …）」という失敗理由**を依頼の `failed` に書く（アプリの「報告に失敗」に出る）。投稿が拒否された・通信できないときも、HTTP の状態などの理由だけが残る（URL は出ない）。
- **二重投稿しない**：アプリが `_rpa_import/done/<バッチ番号>/reported.json` を**先に書いてから**依頼する。印があれば、ブラウザを閉じて開き直しても、同じバッチは報告しない。突合が済んでいて、まだ報告していないバッチ（印も依頼もない）は、開き直したときに再開して1回だけ報告する。
- **報告に失敗しても、取込・突合の結果には影響しない**。画面のバッチの行に「報告に失敗（理由）」と「報告を再送」ボタン（管理者）が出る。
- **取込を依頼した人へのメンション**：報告の最初の投稿の先頭に「@依頼者 EC取込の結果です。」が付き、依頼した人に Teams の通知が届く（確認OKを押すのは依頼した人とは限らないので、本文に「確認OKは、アプリの画面で行ってください」を添える）。仕組み：アプリが `ec_report` の `params.mention`（`{ id: 依頼者のメール(UPN。取込の `requestedBy` と同じ)、name: 表示名 }`）を載せ、`post_teams.py` が Adaptive Card の `msteams.entities`（`{ "type": "mention", "text": "<at>表示名</at>", "mentioned": { "id": メール, "name": 表示名 } }`）と、本文の `<at>表示名</at>` を付ける（最初の1件だけ。続きの投稿には付けない）。**メンション情報が無い・不正な形（メールの形でない・表示名が空など）でも、投稿は成功する**（メンションなしにフォールバック）。表示名・メールは社員の情報で、お客様の名前・住所・電話ではない。専用機の担当が福田さん宛てで付くことを確認済み。
- **投稿先はチャネルでも、チャットでもよい**：ワークフローの「Webhook 要求を受信したらチャネルに投稿する」（チャネル）でも、「Webhook アラートをチャットに送信する」（チャット）でもよい（Webhook の形は同じ。`EC_TEAMS_WEBHOOK_URL` にその URL を入れる）。
- **Teams の Webhook の用意**：チャネルの「ワークフロー」で「Webhook 要求を受信したらチャネルに投稿する」を作り、出てきた URL を専用機の環境変数 `EC_TEAMS_WEBHOOK_URL` に設定する（**細かい手順・権限・URL の有効期限は要確認**）。投稿の形は Adaptive Card のメッセージ（`post_teams.py` の `build_payload`）。
- **差し替え**：専用機の担当が既存の Teams 通知の仕組みに置き換えたいときは、`rpa_jobs.json` の `ec_report` の `script` を別のスクリプト名にする（引数は `--input <本文のJSON> --webhook-env <環境変数名>`。成功は終了コード0、失敗は0以外で理由を標準出力の最後の1行に。URL は出さない）。
